production signing credential, the dry-run validate job checks internal
consistency only, and the release-only publish job behind the protected
`release-publishing` environment re-signs the checksum triples, rebuilds the
native packages with the release trust anchor, validates against the
`AGENT_TRUSTED_KEY_SHA256` pin, and uploads. No product, migration, or web
file changed in any of the three. Every release-path gate below is bound to
the frozen candidate; the retained rows are explicitly marked with the tree
they executed on and why that tree is identical for their path.

## Known non-blocking issues

- `shellcheck` 0.11 (current Homebrew) flags pre-existing warnings in
  `scripts/g6-checkpoint-secret-policy.sh`, `scripts/i18-agent-package-smoke.sh`,
  and `scripts/test-g6-ha-pitr-workflow.sh`; the pinned CI toolchain passes.
  The shellcheck version is not pinned in `toolchains.lock`.
- The rpm leg of the published-baseline upgrade smoke is not implemented
  (the deb leg runs on both release architectures); the rpm cross-version
  upgrade remains covered by the fabricated-version smoke and the native
  package scriptlets are architecture-independent.
- The rollout batch header aggregates failed counts but not a separate
  skipped count; per-node skipped states and reasons are displayed.

## Release blockers

- NONE. The release signing credentials are stored exclusively as
  `release-publishing` environment secrets: the private key was migrated
  from the owner's key material after its public fingerprint was verified
  against the published v0.1.1 release public key, and the repository-level
  copies of both `AGENT_SIGNING_KEY` and `AGENT_TRUSTED_KEY_SHA256` were
  deleted. The only workflow reference is the release-only publish job
  behind the environment's required-reviewer gate, so branch-modified
  dispatch workflows can reach neither value.

## Final verdict

READY FOR v0.2.0.

The frozen candidate satisfies the repository's v0.2 engineering
release-readiness gates: required CI on the exact SHA, migrations on both
PostgreSQL majors, the full package matrix including the real v0.1.1 → 0.2.0
baseline hop pinned to the historical v0.1.1 manifest identity on amd64 and
arm64, a release signing boundary that keeps the production key out of every
dispatch-reachable job with environment-only credential storage, the upgrade
trust boundary and v2 fence, the durable upgrader crash windows, real F3
systemd/privd/PKI evidence, real cross-VM enrollment, browser E2E, and the
formal `production_readiness` G6 verdict on the candidate.

This verdict is a recommendation only. It does not create the `v0.2.0` tag,
the GitHub Release, or any production release asset; publishing remains a
separate, manual action that additionally requires approval of the
`release-publishing` environment deployment.

G6 `production_readiness` evidence is bound to the run's candidate commit
SHA, so the release procedure must verify or rerun the authoritative
production_readiness gate against the final tagged commit before publishing
assets.
