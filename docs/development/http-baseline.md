# HTTP contracts

`internal/api` owns HTTP server assembly, middleware wiring, and resource authorization, while `nodehttp`, `configplanhttp`, and `useroperationshttp` implement their respective handlers and narrow consumer interfaces. Splitting handlers across packages organizes the codebase without replacing runtime authorization checks or breaking up domain transactions.

## Assembly and lifecycle

`api.NewServer(HTTPConfig, backend, build, logger, Modules, Authorization)` builds the HTTP server from validated inputs. In production and full-stack deployments, `newHTTPServer` constructs those inputs, calls `NewServer`, and then invokes the `Enable*` setters (operations, release catalog, user state, privd attestation, enrollment, owner fencing, and local slice) along with `SetLocalSimulatorEnabled` before opening the listener for capabilities that live outside `Modules`. `NewBackend` is a narrow compatibility constructor that initializes default SSE settings and leaves optional modules disabled without running those post-construction setters. Processes started in non-API roles exit before authentication or HTTP server construction begins.

During assembly, the application configures shared domain services, authentication, RBAC, approvals, audit, Certificates, and Plan lookup before instantiating HTTP modules or registering routes. A single `Modules.ConfigPlans` instance satisfies both the business handler and parent approval lookup interfaces, and `Authorization.RBAC` provides both parent and batch authorization guards. When assembly passes a known concrete typed nil, the server treats that capability as disabled instead of substituting a fallback service. Submodules hold only their narrow consumer interfaces and never retain assembly inputs, raw database stores, Transport handles, or a back-reference to the parent Server.

SSE requires explicit, valid configuration at startup; invalid or incomplete settings fail server construction and close any already-allocated resources. Platform and operation hubs share global admission and watcher budgets, start database polling lazily when the first subscriber connects, and do not support runtime reconfiguration or per-request hub construction.

Requests pass through the middleware chain in fixed order: `otelhttp -> requestContext -> limitBody -> timeout -> trackRequests -> routeErrors -> ServeMux -> route wrapper -> handler`. Every `/api/` response defaults to `Cache-Control: no-store`; a handler that sets its own policy overrides it, as the event streams do with `no-cache`. Standard HTTP endpoints run under `http.TimeoutHandler`. SSE streams bypass the request timeout while still remaining tracked for graceful teardown. The server lifecycle claims Shutdown ownership before listening. On shutdown, it closes SSE admission and hubs, initiates HTTP server shutdown, closes active connections once the deadline expires, and waits for in-flight inner handlers to drain. Closed hubs stay mounted on the server, and the HTTP layer never takes ownership of closing the shared database pool or domain services.

## Methods and dispatch

Production method metadata comes directly from ordinary `HandleFunc` registrations. During server construction, `methodRegistrar` forwards each registration once to the underlying root ServeMux before recording the allowed methods; if registration fails, no metadata is published. Duplicate method declarations, unsupported or overlapping route patterns, and mux conflicts panic at startup. Once construction finishes, the routing rules are read-only and isolated per Server.

Route patterns must declare an explicit HTTP method, a hostless path, literal path segments, and full-segment `{name}` wildcards. The registrar rejects subtree patterns, remainder wildcards, `{$}`, partially embedded parameters, percent-escaped literals, dot segments, and structurally equivalent routes that differ only by parameter name. Routes sharing an identical path shape may register different HTTP methods while keeping separate authorization guards per method.

Derived route lookup runs ahead of `compatibilityRouteMethod`, including method denials. The compatibility table retains action-dependent paths for Local-user, session, IP-ban, user, certificate, SecretRef, and approval routes, plus the operation-detail prefix rule, but it cannot override method denials derived for `summary` or `queue-metrics`.

Static routes match the full path string directly. Parameterized routes use Trim/Split matching over `URL.Path` without extra URL decoding or path normalization, passing the original request and parameter names straight through to ServeMux. Registering GET never implicitly enables HEAD. Unknown paths normally return a Problem 404, though certain trailing-slash URLs hit plain-text 404 and doubled leading slashes can return a 307 redirect. Any routing change must preserve authentication and error ordering along with those path-handling differences. `control-plane/internal/api/routes_baseline_test.go` verifies the live route inventory, wrappers, allowed methods, and required permissions directly; historical route counts are not part of the contract.

## Module authorization

Every modular route sits behind an explicit guard that authenticates the caller, enforces browser mutation protections, resolves the target resource and owning workspace, authorizes the specific action, and injects trusted request context. Handlers never trust a client-supplied workspace header on its own to establish authority. Routes that remain on the parent server continue to use central action inference, resource resolution, and periodic SSE revalidation. Request contexts propagate caller cancellation and deadlines all the way into domain services.

| Module | Routes and actions | Consumer capability |
| --- | --- | --- |
| `nodehttp` | List/detail, sessions, IP bans, telemetry: `node.read` | `ListNodesInWorkspace`, `GetNode`, `ListSessions`, `ListIPBans`, `HistoryFrom` |
| `configplanhttp` | Create: `config.plan`; Get: `config.review`; Apply: `config.apply` | `Plans.Create/Get/Apply`, authenticated request values, Secret-use check |
| `useroperationshttp` | Policy GET: `node.read`; policy PUT and batch POST: `user.manage`; batch GET and metrics: `operation.read` | `Operations.GetPolicy/SetPolicy/CreateBatch/GetBatch/Metrics`, `Authorizer.Node/Authorize` |

The `httpx` package provides JSON and Problem response encoding, pagination cursors, UUIDv7 parsing, strict JSON request decoding, and idempotency key extraction without pulling in authentication or domain dependencies. Strict JSON decoding enforces media-type, UTF-8, unknown-field rejection, rejection of exactly repeated object member names, single-value bodies, and the shared request body size limit; a body over that limit returns `413 request-too-large`. Route authorization returns 403 only for an authorization denial and 404 for a missing resource. A resource in a workspace where the caller holds no role binding also returns 404, so the status never confirms that it exists. An explicitly selected workspace the caller cannot see returns 403 whether or not it exists. A role or resource lookup that fails returns `503 database-unavailable` rather than a denial. Node session endpoints return `[]telemetryread.Session` read models instead of telemetry ingestion types.

## ConfigPlan requests

Both Create and Apply call `httpx.RequireIdempotencyKey` to trim the header and return the standard missing-key Problem when the header is blank.

Validation order differs slightly by action. Create checks service availability before parsing the node ID. Apply validates the plan ID, trimmed idempotency key, JSON body, and approval ID before invoking the domain service. If the backing service is disabled, the request fails at that existing validation step after passing outer authentication, Origin verification, and resource authorization. Create responds with a Plan, and Apply responds with an Operation along with its Location and replay headers. A 202 response confirms that the Controller committed the intent to its database; Agent execution on the node remains asynchronous.

When a candidate configuration references secrets, the handler resolves each secret's workspace and caller permission on every request while preserving the `s.devAuth` bypass in development mode. Plans without secret references do not require the Certificates service to be enabled. Referencing a secret when the Certificates dependency is unconfigured returns 503, and any secret lookup, workspace mismatch, or permission failure returns 403 before Create runs. Inside the domain transaction, the service still revalidates stored configuration state, expected version, and node ownership.

A node's `config_revision` is read from `node_config_state.revision`, which tracks configuration state independently of `nodes.version` and `desired_revision`. If no row exists yet, the revision is reported as zero. Database read errors fail the request. The OpenAPI schema leaves the field optional so clients can tolerate older servers. The Web console records a known, nonnegative JavaScript-safe revision alongside the active node and workspace generation and never rebases or automatically retries a stale submission.

Replaying an Apply request for the same Plan and workspace idempotency key reuses the already-committed desired revision and the original command's `expected_version`. A new idempotency key evaluates against live node state. Full intent comparison, revision locking, and approval consumption all occur inside the domain transaction.

Parent approval endpoints obtain `ApprovalBinding/Resource` from the shared ConfigPlan service instance, which evaluates plan validity and expiry and supplies the candidate hash and redacted summary. An unconfigured service or mismatched resource type returns `400 invalid-request`. Unreadable, invalid, expired, and foreign-workspace plans return the same `409 config-plan-not-ready` response before node RBAC checks, which return `403 forbidden` on denial. The `config_plan_summary` payload preserves `plan_id`, `node_id`, `expected_revision`, `candidate_hash`, `materialized_hash`, `current_hash`, `diff_redacted`, and `expires_at`. Approval detail and decision handlers verify all saved authority resources before falling back to the legacy single-resource check. Local password-reset approval requests authorize the action before checking whether the target has a Local credential; unauthorized callers receive the same denial for existing, missing, and non-Local identities.

## User policy and batches

User policy writes validate the idempotency key before decoding JSON, require RFC3339 timestamps with trailing Z and domain validation of fractional seconds, preserve `expected_version` from the request body, trim the reason string, and return 200 with revision ETag and replay headers. Idempotent replays read and return the current policy record. Batch creation returns 202 and Location, preserves caller item order and duplicate entries, and relies on strict JSON decoding to reject any client-supplied `authorized` field.

If a batch references a missing or foreign-workspace node, the entire request is rejected up front. Within the caller's workspace, an item that fails node authorization is recorded on the persisted batch as forbidden, and an authorized item targeting a nonexistent user is recorded as failed/not_found. Development-mode per-item authorization bypass keys off the Principal issuer instead of Server devAuth. A missing, malformed, or non-v7 `X-Approval-ID` header is normalized to nil and never grants approval authority. Item binding, ordering, version checks, and approval consumption execute atomically inside the domain transaction.

Batch reads run existence and workspace-membership checks (returning 404 on mismatch) before evaluating the secondary read permission. The principal who created the batch skips only that secondary workspace-wide check after passing the outer route guard. All other callers must hold `operation.read` in the workspace. Holding node-scoped user management permissions does not grant access to workspace-wide user-operation metrics. Unconfigured service capabilities fail closed after the outer authentication and route guard.

## Upgrade requests

The Operations service owns trusted upgrade target preparation. An unknown node architecture maps to `release-not-trusted` during upgrade execution and `node-not-ready` during approval creation, while node lookup or workspace mismatches return `404 not-found` versus `409 node-not-ready`. Request syntax validation runs ahead of node lookup, architecture resolution, release catalog lookup, and the newer-version check. Creating an approval request does not require the target release to be newer than the node's currently observed version, and single-node upgrade execution may queue work for an offline node, unlike rollout admission.

Idempotent replay of an upgrade request still runs target preparation: if the node's observed version drifted in the meantime, the original intent identity stays the same, but an Agent that has already reached the target version causes the call to return `target-not-newer`. When the Operations service is unconfigured, upgrade approval preparation is disabled. Inside the transaction, version checks, node capabilities, approval consumption, and active-upgrade guards remain with the domain service.

## Verification

Select test suites according to [validation guidance](testing.md). Standard Go unit tests cover server construction, package boundaries, method inventories and path equivalence, failure atomicity, per-server state isolation, SSE admission budgets, and graceful shutdown. Module-level tests exercise the mux against narrow handwritten capability stubs, while full-chain HTTP tests verify request cancellation, timeouts, and in-flight handler draining.

For integrated verification, the `regression-auth`, `backend-policy-api`, and startup test groups run against real Local sessions and restricted runtime database roles to cover Plan Apply and replay, approval and error ordering, Secret access denials, user policy and batch ownership, signed child command intents, upgrade approval bindings, and first-request server assembly. Database owner credentials are used only for test setup and fault injection. Passing on PostgreSQL alone does not prove MySQL compatibility, skipped database tests do not count as acceptance, and HTTP intent tests do not substitute for verifying Agent command execution, package installation, or release readiness.
