# Users, groups and policy

## Desired and observed state

VPN users and groups are scoped to an individual node. The control plane persists desired state, accepts mutations as asynchronous operations, and tracks Agent observations separately. API clients should render the returned convergence status and never treat `202 Accepted` as proof that the change has already taken effect on the node.

Every mutation requires an `Idempotency-Key`, the expected desired version in `If-Match` or the request body, and a reason string; `revision-0` is valid only when creating a brand-new user or group. A new mutation of the same kind can supersede an earlier command for the same resource only while that earlier command is still `queued` and holds no node command lease (a group apply can replace a queued group apply, a password rotation a queued password rotation, a disable a queued disable, and an enable a queued enable, whereas create never supersedes). If a different mutation kind is queued, or if the current revision is already dispatched, accepted, running, unknown, or superseded, the API rejects the request with `409 desired-revision-pending`. Once a revision ends in a failed, expired, rolled-back, or safely rejected state, only a replacement of the same kind is permitted; submitting a different kind returns `409 desired-revision-recovery-required`. The service never merges distinct mutation kinds, because a later command does not carry the earlier command's password ciphertext or lock intent.

Password endpoints accept only a versioned `SealedSecretV1` envelope carrying the `user_password` purpose, the enrolled user-password key ID, and an RSA-OAEP-SHA256 ciphertext; plaintext passwords and legacy untyped ciphertext fields are rejected. Because PKCS#12 export passwords use a separate enrolled key pair and the `certificate_p12_password` purpose, ciphertexts cannot be replayed across the two workflows. On the node, privd keeps both private keys root-only and verifies the signed, typed command envelope before choosing the decryption key.

To apply a password change, the root adapter decrypts the ciphertext with fixed `openssl` arguments and updates a same-directory staging copy of `/etc/ocserv/ocpasswd` using the fixed `ocpasswd` binary. User creation requires the target username to be absent from the authoritative file, whereas password rotation requires the record to exist already. The adapter preserves existing group memberships and lock markers before fsyncing and atomically renaming the staging file into place. Each child process runs under a five-second timeout within an overall 20-second RPC budget. Cancellation-safe cleanup deletes the invocation's uniquely named staging file, and privd purges only recognized stale staging filenames at startup before accepting RPCs. Any conflict, timeout, cancellation, or child-process error leaves `/etc/ocserv/ocpasswd` untouched, and password material or hashes never appear in API responses, telemetry observations, audit events, logs, or traces.

Under plain authentication, `/etc/ocserv/ocpasswd` stores group memberships in the second colon-delimited field of each user line. Applying a group updates that field across every affected user record while preserving password hashes and lock markers, committing via an fsynced same-directory atomic rename. The Agent derives observed groups directly from `/etc/ocserv/ocpasswd` without maintaining a separate sidecar file. Usernames, group names, and member identifiers must match the ASCII regular expression `^[A-Za-z0-9][A-Za-z0-9_.-]{0,63}$`, preventing callers from injecting file paths or executable arguments.

Per-node capacity is capped at 384 managed users, 384 managed groups, 384 authoritative users, 384 authoritative groups, 384 members per group, and 384 total non-sentinel user-to-group memberships. During convergence, telemetry may report up to 768 groups when empty managed-group tombstones coexist with a disjoint set of authoritative groups, and the state API can return up to 1,536 unioned desired and observed records when managed and authoritative names are completely disjoint. Those bounds keep a full authoritative snapshot, its tombstones, and a maximum-size group replacement inside the fixed 64 KiB local RPC frame and 512 KiB telemetry batch. When the Controller has a fresh, complete node snapshot, the API counts the union of desired and observed users and rejects any user creation that would push the node past 384 users. On the node, the root adapter enforces the bound independently: it refuses to create a user against a full `/etc/ocserv/ocpasswd` before decrypting the password or running `ocpasswd`, and it reparses every staged file before recording recovery evidence or renaming the file over the authoritative path. The API similarly rejects oversized group replacements or new managed groups above the limit before creating an operation, and an older Controller that dispatches an oversized payload receives a terminal payload rejection instead of leaving the command in an Unknown state. Nodes whose existing `/etc/ocserv/ocpasswd` exceeds the snapshot bound must trim their local accounts before enrolling, as the Agent refuses to send partial snapshots that could make omitted users appear deleted.

Automatic drift repair is disabled. Instead, privd maintains a bounded, root-only desired-effect store at `/var/lib/ocservia-privd/desired-effects.sqlite3`, authenticated with a dedicated mode `0600` HMAC key and a verified store identity. The database retains the latest record for each mutation kind and target resource, up to 65,536 active rows. Each row binds the command ID, idempotency key, canonical semantic payload hash, revision, expiration timestamp, and authenticated before and after snapshots of the affected `/etc/ocserv/ocpasswd` records, without storing cleartext passwords or password hashes. Applied rows are garbage-collected only after their command TTL can no longer pass Agent expiry validation, while unresolved prepared evidence is kept indefinitely.

Privd commits a `prepared` record before the atomic rename and promotes it to `applied` immediately afterward. Before running any subsequent `/etc/ocserv/ocpasswd` mutation, privd reconciles every authenticated prepared record against the current file on disk: if the file matches the recorded after-state, the record is promoted to applied; if the file still matches the before-state, unrelated mutations are blocked; and any other file state fails closed. Recovery queries return `APPLIED_EXACT`, `SUPERSEDED_BY_NEWER_REVISION`, `ABSENT`, or `UNKNOWN`. Returning `ABSENT` requires an intact, authenticated prepared record whose before-state still matches the live file; a missing row, older snapshot, deleted SQLite file, missing store identity, or modified file always resolves to `UNKNOWN` and never authorizes a retry. Once a newer revision of the same mutation kind is accepted, older payloads become permanently ineligible for retry. Always back up and restore `/var/lib/ocservia-privd/desired-effects.sqlite3` and its HMAC key together, because losing either one leaves in-flight Unknown operations requiring manual operator reconciliation and never permits automatic replay.

In its own SQLite journal, the Agent atomically records each reconciled command result alongside the last applied desired revision for the affected user or group, then includes that revision in its hash-free telemetry snapshots. Resource convergence requires both that reported applied revision and the public state fingerprint to match desired state. While a node is offline with queued commands, its resources remain in `offline_pending`, including password rotations whose public fingerprint does not change on apply. Operators should inspect the linked Operation before deciding whether to submit a replacement revision.

## Quota, expiry and batches

Traffic quotas are expressed in integer bytes up to JavaScript's maximum safe integer (`9007199254740991`). Each policy tracks receive, transmit, or combined bytes over either a UTC calendar month (resetting at `00:00:00Z` on the first of the month) or the account's lifetime; `none` policies always carry a zero byte limit. Account expiration must be an RFC 3339 whole-second UTC timestamp ending in `Z` (zero nanoseconds; timestamps with fractional seconds are rejected without automatic truncation) so operators and background schedulers evaluate the exact same cutoff.

As session telemetry arrives, the Controller converts monotonic per-session byte counters into durable monthly and lifetime usage totals. Duplicate or replayed telemetry batches add zero bytes, and observations older than the stored session cursor are dropped. When a newer observation reports a lower byte count than the cursor (for example after a session or counter reset), the ingestion path starts a new counter epoch and adds the new reading directly instead of guessing what happened in the gap.

Policy enforcement runs in the scheduler under a database-backed leadership lease and a reentrant scan loop, so restarting the scheduler resumes the scan with deterministic idempotency keys. When an account crosses its quota or expiration timestamp, the scheduler enqueues a standard typed `user_disable` desired-state operation and leaves node command serialization to the worker. Uncertain command outcomes follow the normal Unknown reconciliation path. At the start of a new UTC calendar month, the scheduler re-enables a user through a deterministic enable operation only if all of the following hold: the user's policy is monthly and unexpired, an earlier month's quota enforcement under the same policy version disabled the account (and the user is still at that disabled revision, or that enforcement operation is still pending), and current-month usage is below the limit. Accounts that have expired or were disabled by an administrator or another policy revision stay disabled.

User batch operations group a parent batch record with a bounded list of per-user items. Each item is authorized individually and, when permitted, spawns its own child operation and node command. By default, at most 50 remote batch commands may be active globally (configurable from 1 to 500 via `OCSERV_USER_OPERATION_CONCURRENCY`). Worker dispatch reservations are serialized in the database and count only in-flight or unknown commands, so queued commands waiting for an offline node do not tie up global execution slots. The parent batch summary preserves forbidden, failed, unknown, and offline-pending child counts instead of collapsing the batch into a single pass/fail flag. Queued backlog is separately capped at 500 commands per node and 5,000 per workspace, returning a retryable 503 response when full.

Any batch that includes at least one disable item requires independent two-principal approval (enforced across two distinct authenticated principals, credentials, and sessions; see the [approval principal boundary](../reference/stable-contracts.md#approval-principal-boundary)). To submit a disable batch, the caller first generates a UUIDv7 batch ID and requests approval for `user.batch.disable` on that `batch_operation`, passing the complete ordered `batch_items` array in the approval payload. The approval creation response returns the canonical SHA-256 request hash and the normalized item list. Next, a different authorized principal inspects `GET /approval-requests/{approval_id}` and submits the approval decision along with `expected_request_hash`. Once approved, the original caller submits the batch creation request with `X-Approval-ID`; the Controller verifies that both the batch ID and the canonical item list hash match the approval record before consuming it. Batches containing only enable actions do not require approval.

`GET /api/v1/user-operations/metrics` exposes workspace-scoped counters for pending policy enforcements, active batch items, expired worker claims, and unknown items. Configure alerts when `stale_batch_claim_total` remains nonzero across two consecutive scheduler intervals, when `unknown_batch_item_total` rises, or when `policy_pending_total` grows for more than two intervals. Every scheduler pass emits a `user_operations.scheduler.run` trace span and a structured completion log entry; if a pass fails, the process emits `alert_kind=user_operations.scheduler_failed` and exits so the service supervisor can restart it cleanly.

## Recovery

Before intervening manually, stop the scheduler and pause affected API writes, then reconcile any active node commands. Rolling back user or group state is always a forward desired-state mutation: submit the prior group membership list or issue an explicit enable or disable against the current resource revision (enable and disable toggle only the lock marker in `/etc/ocserv/ocpasswd` without touching the password hash or group column). Keep all desired and observed state rows, Agent journals, privd desired-effect records, and policy, usage, batch, and enforcement history intact. Because the repository provides no database down migrations, recover from incompatible database state with a forward fix or a planned [isolated restore](../operations/incident-recovery.md#database-recovery).
