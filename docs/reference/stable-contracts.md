# Current contracts and acceptance

## v1.1.0 transition

The published [v1.1.0 policy reset](support-policy.md#v110-policy-reset) replaces the software-version windows, historical release matrix, and schema-compatibility admission rules from the 1.0 policy, removing the software-version guards and legacy compatibility entrypoints. While the [release notes](https://github.com/GentleKingson/ocservia/releases/tag/v1.1.0) record acceptance for `v1.1.0` itself, every subsequent candidate must pass its own validation. Runtime protocol negotiation, command authorization, artifact digest checks, durable state invariants, migration content integrity, and live readiness probes remain active contracts without acting as a software-version fence.

## Current candidate scope

Each candidate build is validated against its exact artifacts on the supported architectures, deployment modes, and database engines. Matching version strings, unchanged protocol numbers, or passing unit tests do not guarantee cross-version runtime compatibility. Historical matrices, exclusions, and test records from the 1.0 line remain archived in the [published 1.0 inventory](https://github.com/GentleKingson/ocservia/blob/d420b22018596d6741d55fa56bd19c4a767e5817/docs/reference/stable-contracts.md); the entrypoints removed after 1.0 are no longer part of current acceptance, while existing published release artifacts remain unchanged.

## Schema sources and generation

[`openapi/openapi.yaml`](../../openapi/openapi.yaml) and the Protobuf definitions under [`proto/`](../../proto/) are the normative sources for HTTP endpoints, messages, and field tags. Running `make generate` (`scripts/generate.sh`) regenerates `control-plane/gen/proto`, `rust/crates/contracts/src/generated`, and `web/src/api/generated`; never edit files under those generated directories by hand. The local `Agent`/`privd` IPC protocol is maintained as handwritten Rust types in `rust/crates/agent-protocol`. Local `oneOf` map handling for the web client is documented in the [TypeScript template override](../../openapi/templates/typescript-fetch/README.md).

Toolchain setup is covered in [validation guidance](../development/testing.md). Contract breaking checks (`scripts/check-breaking.sh`, which diffs against `origin/main` while honoring the explicit security-migration allowlist) and generated-code cleanliness checks (`scripts/generated-clean.sh`) run as manual verification entrypoints outside Basic CI; see [GitHub Actions validation](../development/github-actions.md) for CI job routing. Passing a schema diff check does not replace release-level behavioral testing.

## Approval principal boundary

The Controller enforces, and Business Smoke exercises, two independently authenticated principals (requester and approver) at the credential and session layer, without claiming organizational two-person custody. Each principal authenticates with distinct credentials in its own session and must pass workspace and RBAC checks. Approvals bind to the exact request hash, target resource, and expected revision; self-approval is rejected with HTTP `403`, and consumed approvals cannot be replayed or widened. Supplying two user IDs without separate authenticated sessions does not satisfy this boundary. Likewise, while the [Local bootstrap procedure](../operations/authentication.md) creates two distinct accounts, it cannot verify how many human operators hold those credentials.

Automated validation suites may drive both principals across separate authenticated sessions, and their reports must record that run as simulated two-principal acceptance. Verifying that two distinct people hold custody of the credentials belongs to an operator's enterprise security procedure outside automated Business Smoke. Production operators must assign requester and approver credentials to different natural persons: one person must not hold credentials for two approval-capable principals, whether through a second Local account, an OIDC identity alongside a Local account, or any other identity source. Regardless of custody model, runtime RBAC, payload-bound approvals, self-approval rejection, and replay protection remain active.

## Current application acceptance

Candidate builds are gated by [Release Check](../development/release-checks.md), which covers native packages, business workflows, integration suites, security scans, and single-instance resilience checks. The project does not maintain a cross-version native upgrade or migration matrix; target-version regression fixtures test the upgrade mechanism itself without promising compatibility with historical releases.

Nodes that advertise `ocserv.config.complete.plan` and `ocserv.config.complete.apply` follow the [complete node-local TLS profile](../development/configuration.md#node-local-tls-provisioning). Because `Apply` performs a daemon reload only, startup-only settings (authentication mode, listeners, worker privilege settings, socket paths, and TLS file paths) must match the active protected configuration; initial activation or changes to those startup-bound settings require an authorized maintenance restart. Acceptance requires end-to-end VPN client authentication, verified rollback, and durable state recovery beyond simple config-parser or `occtl` status checks.

### Matched-release recovery boundary

Even when the Controller, `transportd`, `Agent`, `privd`, and `upgrader` all come from the same release, an interrupted non-idempotent mutation is not guaranteed to self-heal automatically. Seeing the node online with a fresh fenced session and a healthy `ocserv` process does not prove whether an in-flight reload ran before the interruption or whether re-running it is safe.

Automated query-only reconciliation (`RECONCILE_ONLY`) can settle an ambiguous command only when it recovers an authenticated `privd` receipt or an existing terminal entry in the `Agent` journal. It never infers completion from current daemon health, missing error logs, or database row timestamps. Before marking an operation terminal, reconciliation verifies the exact command ID, semantic hash and version, operation/idempotency identity, authorization revision, owner-fence lineage, `Agent` journal entry, and signed root receipt; if any piece is missing or inconsistent, the operation remains `Unknown`.

While an operation is `Unknown`, operators must pause conflicting writes to that node or resource. Do not delete the local SQLite journal or root effect store, hand-edit database tables, reset node `EndpointID`s, or resubmit the mutation under the same or a new idempotency key. Read-only reconciliation queries are safe, and the explicit `RetryIfEffectAbsent` path may be used only after cryptographic proof confirms that no privileged effect occurred on the host (a stopped or healthy daemon does not by itself prove effect absence, and upgrading the node package does not reconcile pending commands). Step-by-step operator instructions are in the [incident recovery procedure](../operations/incident-recovery.md#transport-and-credentials).

In automated validation suites, strict recovery probes keep their recorded pass/fail status: a later passing run does not clear an earlier `Unknown`, and a scoped `EXPECTED-UNKNOWN` classification requires captured evidence of the unresolved command, query-only reconciliation, preserved node identity and journal state, absence of duplicate mutations, and paused conflicting writes. Missing test evidence is recorded as `NOT RUN` or `BLOCKED`.

## CI and rollout decisions

Release qualification follows [Release policy](../development/release-checks.md). Removed 1.0 compatibility gates are retired by policy and must not be reported as skipped passes.

Across all rollouts, preserve node trust records, negotiated capabilities, independent two-principal approvals, Signer identity and revision counters, local command journals, root receipts, and owner-fence floors. Reconcile any `Unknown` operations before issuing new mutations to the same target, and use only the documented install, upgrade, and rollback entrypoints without reversing SQL migrations or resetting persistent identities. Unrun, failed, skipped, and out-of-scope checks are tracked separately, and any commit change invalidates prior CI results for the affected suites.
