## A/B/C/D Decision

- A, unchanged direct reuse: none.
- B, adapter behavior: [dashboard #183](https://github.com/mmtaee/ocserv-dashboard/pull/183)
  serializes password writes. Privd already constructs one Adapter and shares
  its `Arc<Mutex>` across requests. User create, password rotation, enable,
  disable and group changes hold that same lock across read, staging and
  publication. No second global lock is needed. This is not a cross-process
  lock: operators must not run independent ocpasswd writers against the managed
  file while privd is accepting mutations.
- C, re-expressed product semantics: #183 records only successful restore items,
  continues after individual failures, and stops submitting when cancelled.
  Ocservia has no dashboard backup-upload API. Its existing user batch service
  retains item outcomes, stable child idempotency keys, bounded claims and
  `partial_failed`/`unknown` states. UserState commits desired revision, command,
  outbox and audit together. A queued operation is not node-side success.
- D, rejected implementation: upstream GORM transactions around local commands,
  synchronous restore and its HTTP timeout exemption are not imported. Long work
  continues through operations/outbox. [Dashboard #182](https://github.com/mmtaee/ocserv-dashboard/pull/182)
  converts another product's legacy SQLite/password data and repairs files
  directly; no legacy importer or arbitrary path/shell capability is added.

## Adapter Boundaries

The existing same-directory unique staging file, descriptor-relative no-follow
publication, owner/mode/link checks and authenticated desired-effect store remain
the write authority. Prepared whole-file transitions are resolved before another
mutation. Privd's authenticated cached response and the Agent journal remain the
authorities for exact replay; file observation alone cannot invent a successful
signed receipt. An uncertain post-effect/pre-receipt crash remains Unknown.

The adapter also owns ocpasswd's adjacent `<staging>.tmp` lifetime. Timeout or
cancellation removes it; startup removes only private, correctly owned,
single-link files matching the exact generated UUIDv7 namespace (including the
`.tmp` suffix). Unsafe legacy leftovers fail closed, rather than relaxing file
checks. Privd's `UMask=0077` establishes a restrictive process-wide default.
[Ocpasswd 1.5.0](https://gitlab.com/openconnect/ocserv/-/blob/1.5.0/src/ocpasswd/ocpasswd.c)
sets its own `umask(066)`, keeping newly created scratch files at `0600` before
final normalization to `root:root`. The Unix socket still receives explicit
`0660` permissions. Configuration publication explicitly restores the original
file mode after creation, independently of umask.

One adapter deadline covers child stdin, process exit and both output pipes.
Cancellation retains the process-group kill guard, including when the parent
has exited but a descendant still holds a pipe. Request deadlines are not
disabled or extended.

## Minimal Compatibility Target

T02 selected the latest stable [Ocserv 1.5.0](https://gitlab.com/openconnect/ocserv/-/releases/1.5.0),
source commit `49f9956eeeffd613e4bcac3f6450c682ec21e75a`. The
[official manual](https://ocserv.gitlab.io/www/manual.html) describes plain-file
authentication, configuration validation and certificate/P12 usage; its page
version is older than the release, so the tagged source and actual binaries are
the output-format authority.

The minimum targeted acceptance combination is source-built 1.5.0 on Debian 12
Linux ARM64, with real ocserv, occtl, ocpasswd, OpenConnect and OpenSSL. This is
an isolated adapter compatibility target, not a newly certified production
distribution or native systemd installation. The existing 1.2/1.3/1.4 parser
fixtures remain regression inputs, not proof that those packages implement all
commands or contain required security patches. Only exact 1.5.0 is added to the
version parser; unreleased 1.5.1 is not implicitly accepted.

Actual production package versions, distro backports and external authentication
configuration still belong to deployment inventory. In particular, unreleased
per-user/group path hardening is not silently imported into Ocserv. Managed
names remain validated at the existing Controller and privileged boundaries;
external authentication/configuration sources require their own applicability
review. Unrelated upstream features do not become 1.0 blockers.

## Verification and Rollback

Use a task-isolated checkout on BuildServer, following
[the validation guide](../development/testing.md). Do not install Ocserv on the
shared host. The focused entry points are:

- `cargo test --locked -p ocservia-ocserv-adapter -p ocservia-privd`: deadline,
  cancellation/scratch cleanup, file permissions, configuration rollback,
  authenticated recovery, exact replay, CSR and encrypted P12 behavior.
- `scripts/i13-native-ocserv-integration.sh`, in a disposable Linux environment
  with native Ocserv and TUN: real password authentication before/after rotation,
  disable/enable, group routing, occtl output parsing and session termination, simultaneous same/different
  users and group/password writes, hash/lock preservation and replay. No
  host-installing Agent smoke is involved.
- `TestUserOperationsBackendIntegration`, using a disposable supported database:
  partial batch outcomes, failed items, durable child recovery and no duplicate
  command/outbox/audit intent. Database state fixtures do not claim real node
  execution or full backup restoration.

Keep per-run SHA, patch digest, binary/image identities, versions, commands,
statuses and limitations with task evidence, not in this maintenance document.
Fixture crash-window tests are not physical power-loss or cross-host acceptance.

No schema, wire contract or new privileged operation is introduced. To revert,
stop dispatch, reconcile retained operations and restore the prior matched
Agent/privd package through the existing lifecycle. Preserve the root effect
store, HMAC/receipt keys and Agent journal. Reverting the parser also removes
1.5.0 version recognition; do not deploy that rollback against a 1.5.0-only
target without accounting for this limitation. Prefer retaining the restrictive
umask and scratch cleanup fixes. Removing this inventory alone has no runtime
effect.
