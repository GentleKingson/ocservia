## Reuse decisions

- **A, direct reuse:** none.
- **B, adapter behavior:** [dashboard #183](https://github.com/mmtaee/ocserv-dashboard/pull/183)
  serializes password writes. Privd already shares one Adapter's `Arc<Mutex>`
  across create, rotation, enable/disable and group changes, covering read,
  staging and publication. This is not a cross-process lock: independent
  ocpasswd writers must not modify the managed file while privd accepts writes.
- **C, product semantics:** successful-item accounting, partial failure and
  cancellation use the existing asynchronous [user batch service](../development/user-management.md#quota-expiry-and-batches).
  Ocservia has no dashboard backup-upload API. Stable child idempotency keys,
  bounded claims and retained item outcomes distinguish queued work from success.
- **D, rejected:** GORM transactions around local commands, synchronous restore
  and its HTTP timeout exemption. [Dashboard #182](https://github.com/mmtaee/ocserv-dashboard/pull/182)
  is a legacy SQLite/password importer for another product; it does not justify
  adding arbitrary path/shell access or an importer here.

## Adapter safeguards

Publication retains same-directory unique staging, descriptor-relative no-follow
access, owner/mode/link checks and authenticated desired-effect evidence.
Prepared transitions are resolved before another mutation. Exact replay requires
the authenticated privd response or Agent journal; file observation cannot
invent a signed receipt. Uncertain post-effect/pre-receipt crashes stay Unknown.

Timeout/cancellation removes ocpasswd's adjacent `<staging>.tmp`. Startup only
cleans private, correctly owned, single-link UUIDv7 staging names, including
their `.tmp` suffix; unsafe legacy leftovers fail closed. Privd uses
`UMask=0077`; [Ocpasswd 1.5.0](https://gitlab.com/openconnect/ocserv/-/blob/1.5.0/src/ocpasswd/ocpasswd.c)
uses `umask(066)`, creating scratch files at `0600` before root ownership
normalization. The socket explicitly uses `0660`; configuration publication
restores the original mode. One deadline covers child stdin, exit and output
pipes, with a process-group kill guard even when descendants outlive the parent.

## Compatibility and validation

The isolated adapter target is source-built Ocserv **1.5.0**, commit
`49f9956eeeffd613e4bcac3f6450c682ec21e75a`, on Debian 12 Linux ARM64 with real
ocserv, occtl, ocpasswd, OpenConnect and OpenSSL. Tagged source and binaries,
not the older manual page, determine output formats. This does not certify a
production distribution or native systemd install. The 1.2/1.3/1.4 fixtures are
parser regressions, not package/security acceptance; 1.5.1 is not implicitly
accepted. Production versions, distro backports and external authentication
remain deployment-specific. Unreleased path hardening is not imported; managed
names retain Controller and privileged-boundary validation.

Use an isolated BuildServer checkout and disposable Linux/TUN environment,
following [testing](../development/testing.md), without installing Ocserv on the
shared host. Focused checks are:

- `cargo test --locked -p ocservia-ocserv-adapter -p ocservia-privd`: deadlines,
  cancellation, scratch cleanup, permissions, rollback, authenticated recovery,
  replay, CSR and encrypted P12.
- `scripts/i13-native-ocserv-integration.sh`: real authentication, rotation,
  lock/group changes, occtl parsing, termination, concurrent writes and replay;
  no host-installing Agent smoke.
- `TestUserOperationsBackendIntegration`: partial outcomes and durable child
  recovery without duplicate command/outbox/audit intent. Database fixtures do
  not establish real node execution or full backup restoration.

Keep run identities and results in task evidence. Fixture crash tests do not
establish physical power-loss or cross-host acceptance. No schema, wire contract
or privileged operation was added. For rollback, stop dispatch, reconcile work
and restore a matched Agent/privd pair while preserving root effect evidence,
HMAC/receipt keys and the journal. Reverting the parser removes 1.5.0 recognition;
account for that on 1.5.0-only targets. Retain restrictive umask and scratch
cleanup where possible. Removing this inventory alone has no runtime effect.
